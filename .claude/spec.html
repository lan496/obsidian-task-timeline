Task Timeline - Spec v1

Design reference for the Markdown parser and data model behind the timeline view.

End-user behavior (how to open the view, settings, interaction model, example tasks) lives in the project README. This document is the internal spec for what the parser must accept, the precedence rules between syntaxes, and the shape of the parsed task records.

Goals

  • Surface every dated task in the vault on a single horizontal timeline.
  • Support date ranges as a first-class feature: a task with a start and a due date renders as a multi-day bar spanning [start, due]. Ranges are the primary reason this plugin exists; a point-in-time bar is just the degenerate single-day case.
  • Reuse the date syntax already used by uphy/obsidian-reminder, obsidian-community/obsidian-kanban, and the obsidian-tasks due emoji verbatim, extended with a dash-separated two-date form for ranges. The plugin does not introduce a new storage format and does not require a settings step before existing notes show up.
  • Keep the view live: edits to a Markdown file are reflected in the timeline without manual refresh.
  • Allow jumping from a bar back to the exact line in the source note (and to the linked page when one is set).

Non-goals (for v1)

  • Editing tasks from the timeline (drag-to-reschedule, inline rename). Read-only navigation is enough to validate the design.
  • Dependencies / arrows between tasks.
  • Custom grouping by tag, folder, or note property. The v1 grouping is by note (file).
  • Recurring tasks, sub-tasks rolled up into parents, or status workflows beyond [ ] / [x].
  • Mobile-first layout. Desktop is the primary target; the view should still open on mobile but is not tuned for narrow screens.

Data model

Source of truth

Tasks live in Markdown files. The plugin never writes to them in v1. The authoritative scan reads app.vault.getMarkdownFiles() and parses each file on demand (cached read).

Task forms

Both forms below are first-class. The form a line takes determines where its label comes from and where its dates come from; neither is preferred over the other.

FormLabel sourceDate sourceClick target
Inline
- [ ] text + marker		 checkbox text, with the date marker stripped the inline date marker (see Task syntax) the host file, scrolled to the checkbox line
Linked-page
- [ ] [[Page]] (the body is a single wiki link, nothing else)		 page title, or the alias when [[Page|Alias]] is used the linked page's start / due frontmatter properties (YYYY-MM-DD) the linked page

Mixed cases:

  • If the checkbox body contains a wiki link and other text, it is treated as an inline task (the link becomes part of the label, and dates come from inline markers on that line).
  • An inline task with no due-date marker is skipped. A linked-page task whose target page has no due property is also skipped.

Task syntax

A task is any list item matching ^\s*[-*]\s+\[( |x|X)\]\s+(.*)$. Inline tasks carry one date marker, in one of the three forms below. Each form accepts either a single date (a point-in-time task) or two dates joined by - (a range, start - due).

The single-date forms are taken verbatim from the upstream plugins; the table cites the exact spec page that defines each one. The two-date variant is a Timeline extension on top of the same marker.

Source pluginSingle dateRangeReference
obsidian-reminder (native)(@YYYY-MM-DD)(@YYYY-MM-DD - YYYY-MM-DD)Set reminders
obsidian-reminder ↔ Tasks (due emoji)Due YYYY-MM-DDDue YYYY-MM-DD - YYYY-MM-DDInterop with Tasks
obsidian-reminder ↔ Kanban@{YYYY-MM-DD}@{YYYY-MM-DD - YYYY-MM-DD}Interop with Kanban

The Tasks-style row uses the calendar emoji as the marker; the parser matches it literally (code point U+1F4C5).

The Kanban plugin's default trigger is @, which expands at edit time into the bracketed @{YYYY-MM-DD} markdown stored on disk. The Reminder plugin reads the same bracketed form, which is the form this plugin parses.

A task with no recognized due date is skipped entirely. When a task carries more than one due-date marker, first-match-wins in the table order - the Reminder-native form is preferred over the Tasks-style emoji, which is preferred over the Kanban form.

Date ranges

A range is two ISO dates joined by - (space-dash-space) inside any of the three marker forms above. Rules:

  • The first date is the start; the second is the due date.
  • Both dates use the same YYYY-MM-DD form.
  • The dash separator must be surrounded by whitespace (YYYY-MM-DD - YYYY-MM-DD) so it cannot be confused with the dashes inside an ISO date.
  • If start > due, the task is treated as a single-day bar on the due date.

The range form is a Timeline-specific extension on top of the upstream single-date markers; the Reminder plugin will treat the second date inside its bracket as plain text, and similarly for Kanban. That is acceptable: the upstream plugins keep firing on the first date as a reminder/due-date anchor, while Timeline reads the full range.

Internal types

type DueDateSource =
  | 'page-property'      // from the linked page's `due` frontmatter
  | 'reminder'           // inline `(@YYYY-MM-DD ...)`
  | 'tasks'              // inline due emoji
  | 'kanban';            // inline `@{YYYY-MM-DD}`

type TaskForm = 'inline' | 'linked-page';

interface ParsedTask {
  form: TaskForm;
  label: string;         // checkbox text (inline) or page title / alias (linked-page)
  hostPath: string;      // vault-relative path of the file containing the checkbox
  hostLine: number;      // 1-indexed line of the checkbox
  pagePath?: string;     // resolved path of the linked page (linked-page form only)
  column?: string;       // most recent Markdown heading above the checkbox
  done: boolean;
  due?: string;          // YYYY-MM-DD; required to appear on timeline
  start?: string;        // YYYY-MM-DD; absent for single-day tasks
  dueSource?: DueDateSource;
}

A task with due is considered "dated". When start is present and start <= due, the bar spans [start, due] inclusive; otherwise the bar is a single day on due. All date math operates on calendar days; time-of-day in the source markup is ignored.

hostPath:hostLine always points at the checkbox. For an inline task, clicking the bar jumps there. For a linked-page task, pagePath is the resolved target of the wiki link; clicking the bar opens the page. The column field records the most recent Markdown heading above the checkbox so the view can group / filter / color kanban-style boards.

Open questions

  • Range syntax is a Timeline extension. The dash-separated two-date form is not part of the Reminder, Tasks, or Kanban syntax. Upstream plugins will read only the first date inside the marker as their anchor. If the upstream plugins later formalize a range syntax, this plugin should follow it instead.
  • Configurable triggers. Kanban lets the user remap its date trigger in settings; Reminder's bracketed-form parser does not depend on that, but a non-default Kanban setup will emit markdown the Reminder plugin (and this plugin) won't recognize. v1 assumes defaults and surfaces this limitation in the settings tab.
  • Done date. Reminder's Tasks interop also recognizes the completion emoji (U+2705 YYYY-MM-DD). v1 ignores it for placement (the bar positions on the due date) but it could feed a future "actual vs. planned" decoration.
  • Property-only pages (no checkbox). v1 only surfaces tasks that have a checkbox line somewhere - either an inline task with date markers, or a - [ ] [[Page]] line pointing at a dated page. A page that has due: set but is never linked from a checkbox will not appear. Adding a "discover any page with a due property" mode is the obvious next step but expands the scan surface a lot, so v1 keeps the checkbox as the entry point.
  • Property key configurability. v1 hard-codes due and start as the property keys. A future setting could remap them (e.g. dueDate, endDate).
