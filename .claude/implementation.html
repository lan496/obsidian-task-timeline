Task Timeline - Implementation v1

How to build what spec.html describes.

This document covers the module layout, rendering math, live-update strategy, performance budget, and the milestone breakdown.

Architecture

+--------------------+      +---------------------+      +----------------+
| MarkdownFile cache | ---> | TaskParser          | ---> | TaskStore      |
| (vault events)     |      | (regex + date scan) |      | (in-memory)    |
+--------------------+      +---------------------+      +-------+--------+
                                                                  |
                                                                  v
                                                         +--------+--------+
                                                         | TimelineView    |
                                                         | (renders bars)  |
                                                         +-----------------+

Modules

  • tasks/ - pure parsing. No Obsidian imports below readMarkdownDocuments. Easy to unit-test by feeding MarkdownDocument fixtures.
  • timeline/ - date math and layout primitives (day offset, range enumeration, zoom-to-pixel-width). Pure functions.
  • views/TaskTimelineView - Obsidian ItemView. Owns DOM creation and subscribes to the TaskStore.
  • store/TaskStore - new in v1. Holds the parsed task list, exposes subscribe(listener), and re-runs parsing for a single file when Obsidian emits a vault event for it. The view re-renders on every store update.
  • main.ts - plugin entry; wires the store to vault events (vault.on('modify' | 'create' | 'delete' | 'rename')) and registers the view + command.

Rendering

  • The timeline pane is a horizontally scrollable <div> whose width equals (totalDays * dayWidth). A sticky header holds the date axis.
  • Each task is one row. The bar is an absolutely positioned <div> inside the row, with
    • left = offsetDays(start ?? due) * dayWidth
    • width = (durationDays * dayWidth) - gutter
    where durationDays = diffDays(start ?? due, due) + 1. Single-day tasks collapse to width = dayWidth - gutter.
  • Rows in the sidebar share the same height as rows in the timeline pane and scroll vertically together (a single scroll container wraps both columns; only the timeline column scrolls horizontally).
  • CSS lives in styles.css and uses Obsidian's theme variables (--background-modifier-border, --text-muted, etc.) so the view inherits the active theme.

Zoom math

The zoom toolbar sets a dayWidth value (see the spec's defaults table). Whenever it changes:

  1. Record the date currently at the viewport's horizontal midpoint (using the old dayWidth).
  2. Apply the new dayWidth; recompute totalDays * dayWidth and the bar positions.
  3. Scroll so that the recorded date sits back at the viewport midpoint under the new scale.

The axis header switches its tick cadence based on the active level but the underlying coordinate space is still per-day, so bars never need re-positioning when only the cadence changes.

Live updates

Re-parsing the entire vault on every keystroke is wasteful. The plan:

  1. On plugin load, parse all Markdown files once and seed the store.
  2. Listen for vault.on('modify', file):
    • If the modified file contains checkboxes, re-parse its tasks.
    • If the modified file is the target of any task's wiki link, re-resolve the dates for those tasks (its properties may have changed).
    To support the second case efficiently, the store maintains a reverse index from pagePath to the set of tasks that link to it.
  3. On create / delete / rename, mutate the store accordingly. Renames update both hostPath and any pagePath pointing at the old name.
  4. The view subscribes to store changes and rebuilds its DOM. For v1 this is a full rebuild; if it becomes a bottleneck we can diff by task id (hostPath:hostLine).

Performance budget

  • Target vault: 5,000 notes, 2,000 dated tasks. Initial parse should finish under ~500 ms on a warm cache.
  • Rendering 2,000 absolutely-positioned bars is fine in modern browsers; no virtualization in v1, but the row container is the natural unit if we need to add it later.

Milestones

M1 - Inline task parsing + single-day view

Extend the existing parser to detect all three due-date syntaxes on inline checkbox text (Reminder-native bracketed form, Tasks-style due emoji, Kanban-style @{...}), add unit tests, and render single-day bars. (Most of the existing src/ covers this; it needs tests and small cleanups.)

M2 - Linked-page tasks

Detect - [ ] [[Page]] bodies as a parallel task form, resolve the link via metadataCache, read due / start from the linked page's note properties. Reverse index for change tracking. Tests for alias links, broken links, mixed cases (link + extra text becomes inline), and the no-property case.

M3 - Ranges

Add the dash-separated two-date form inside each of the three inline markers, and start: property reading for linked-page tasks. Include the range-validity check (start <= due) and bar-width math. Unit tests for start-after-due, start-equals-due, and dash inside vs. outside an ISO date (the surrounding-whitespace rule).

M4 - Live updates

Introduce the TaskStore, wire vault events, handle both checkbox-file and linked-page modifications, debounce re-renders.

M5 - Zoom + jump-to-source

Day / Week / Month / Quarter / Year zoom toggle, two-row sticky axis header, scroll-position preservation on zoom change, click bar to open the linked page or the checkbox line.

M6 - Settings

Folder include/exclude, persisted settings tab (default zoom level, per-level day widths, start-of-week).

Development

  • npm i to install dependencies.
  • npm run dev to build in watch mode. The build copies main.js, manifest.json, and styles.css into the configured test vault.
  • npm run lint runs ESLint with the Obsidian plugin rules.
  • npm run build runs tsc --noEmit then a production esbuild.

Manual install: copy main.js, styles.css, and manifest.json into <vault>/.obsidian/plugins/obsidian-task-timeline/ and enable the plugin in Obsidian's community plugins settings.
